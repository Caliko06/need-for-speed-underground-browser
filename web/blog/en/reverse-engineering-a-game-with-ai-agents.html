Reverse engineering a game with AI agents: the rules that keep it exact

One person directs the project; AI coding agents do most of the reading, writing and testing. That works only because a wrong guess cannot survive the checks below.

Updated November 21, 2026

Who does what

  • The owner chooses the direction, plays every build and says yes or no.
  • Claude (Anthropic's Claude Code) plans, reads the binary and writes most of the translator and the host.
  • Codex (OpenAI) takes whole slices in parallel: a subsystem, a tool, a test.
  • OpenCode with DeepSeek handles cheap, wide jobs: search the decompiled code, fill a census table, run a batch.

The risk: a confident guess

A language model can write a plausible offset or a plausible file format that is simply wrong, and a game built on wrong values fails far away from the mistake. These checks exist to stop that:

  • Proof or UNKNOWN. Every value, format or patch names what proves it: an address read with REA (a reverse engineering server agents use over MCP) plus a second tool such as Ghidra or Hopper. Unproven means UNKNOWN, and nothing is built on it. More in reading the binary.
  • A machine judge. The translator's output is compared bit for bit with a reference x86 CPU. An agent cannot argue with a mismatch. See static recompilation.
  • Loud failures. A missing instruction or a missing DirectX method stops the game with its name, so a gap shows the first time it runs.
  • Real runs. A change is checked in a headless, muted Chrome that boots the real game and takes screenshots, and the owner judges by playing.
  • One state file. A plan file lists every step with its state and its evidence. Every session starts from it, not from memory.

The code is public on GitHub.
